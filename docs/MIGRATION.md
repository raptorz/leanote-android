# Flutter 移动端迁移方案

## 目标

在 `mobile-app` 根目录维护新的 Flutter 客户端，用一套业务代码支持 Android 和 iOS。旧 Java Android 工程归档在 `legacy-android/`，只作为功能清单和交互参考。

新客户端以 desktop 的离线优先模型为基础，同时针对手机小屏重新设计导航，不直接照搬桌面三栏布局。API 固定使用 API2 v1.0.0，不兼容旧 `/api`，也不迁移旧 Android SQLite 数据；用户首次登录后从服务端重新建立缓存。

## 架构

- `core/api`：API2 JSON 客户端、错误分类和版本协商
- `domain/models`：账号、笔记本、笔记等领域模型
- `data/database`：每账号隔离的 SQLite 离线数据
- `data/session`：系统安全存储中的 token
- `sync`：上传本地 dirty 数据、拉取 USN 增量、重新同步和附件后台任务
- `repositories`：组合网络、缓存和同步，向界面提供稳定操作
- `ui`：适配手机的页面和组件

账号缓存主键由规范化服务端地址和服务端用户 ID 共同组成。任何笔记、笔记本、标签及附件与服务端交互时使用服务端 ID，本地主键仅用于数据库内部关系。

## 实施阶段

### 第一阶段：工程与只读闭环

- [x] 归档旧 Android 工程
- [x] 创建 Android/iOS Flutter 工程
- [x] 配置 Android 网络权限与中英文应用名
- [x] 实现一次 API2 登录返回 token、用户资料及版本信息
- [x] 实现笔记本、含正文笔记、标签分页下载
- [x] 实现 SQLite 原子快照和安全 token 存储
- [x] 实现登录页、笔记本页、笔记列表和空状态
- [x] 增加 API 合同与数据库测试
- [x] 完成笔记详情及 Markdown 原文/富文本只读渲染

### 第二阶段：编辑与离线同步

- 笔记与笔记本的新增、编辑、移动、删除和星标
- 自动保存到 SQLite，并记录 dirty、new、deleted 状态
- 增量同步先上传本地 dirty 数据，再按 USN 下载服务端变化
- 元数据冲突以服务端为准；正文冲突保存本地副本
- 完全同步负责合并；重新同步清空当前账号缓存后重新下载
- 同步进度、失败提示和未同步状态

### 第三阶段：完整移动功能

- 标签、搜索、历史版本和共享笔记
- 图片和附件上传、预览、下载及后台并行缓存
- 用户资料、头像、密码和语言设置
- 离线附件、系统分享、深链和生物识别解锁等适合移动端的能力
- Android/iOS 通知、生命周期和后台任务适配

### 第四阶段：发布

- 使用 Gemsnote 正式图标生成 Android adaptive icon 和 iOS AppIcon
- Android 签名、AAB/APK 构建和 iOS 签名归档
- 真机离线、弱网、升级、冲突及大数据量回归测试
- GitHub Actions 自动测试；Android 自动构建，iOS 使用 macOS runner 构建

## 小屏交互

手机端采用逐层导航：工作区/标签/搜索 → 笔记列表 → 笔记详情或编辑。笔记本树在独立页面展开，常用的新建、同步和搜索放在页面工具栏或浮动按钮中。平板宽度充足时可逐步增加双栏布局，但不以桌面三栏作为手机最低布局。

## 旧版值得保留的功能

- Markdown 与富文本笔记
- 离线阅读和编辑
- 搜索、标签、星标、附件和历史版本
- Android 系统分享、桌面小组件等移动端能力

旧版注册、旧 API、旧数据库迁移、博客和演示账号功能不进入新客户端。
